--------------------------------------------------------------------------------
  PROBLEMA RAIZ: ARQUITETURA QUEBRADA (State Isolation)
--------------------------------------------------------------------------------

O problema central era que ShoppingForm e ShoppingList viviam em "bolhas"
separadas — cada um com seu próprio estado, sem canal de comunicação.

  ShoppingForm         ShoppingList
  [estado: cart]       [estado: mockShoppingList]
       |                        |
       v                        v
   renderiza                renderiza
   (visível só             (lista fixa
    para ele)               do seed)

A solução correta em React para este caso é o padrão "Lifting State Up"
(levantar o estado): o estado da lista sobe para o componente pai (App),
que passa os dados para baixo via props para ambos os filhos.

  App
  [estado: shoppingList]  <-- única fonte da verdade
       |              |
       v              v
  ShoppingForm    ShoppingList
  (recebe onAdd)  (recebe items + onRemove)

Desta forma, quando o formulário chama onAdd(), o App atualiza sua lista,
e o React re-renderiza ShoppingList automaticamente com os dados novos.


================================================================================
  PARTE 1 — App.tsx: Levantamento de Estado e Limpeza
================================================================================

Arquivo: src/App.tsx
Status: CONCLUÍDO

Decisões tomadas:

  1. Estado único da lista
     Criado um único useState<ShoppingItem[]>([]) iniciando com array vazio.
     O motivo de iniciar vazio (e não com mockShoppingList) é que a atividade
     pede um app funcional de lista de compras — o usuário deve adicionar seus
     próprios itens, não ver dados de teste pré-carregados.

  2. Função adicionarItem
     Criada dentro do App e passada para ShoppingForm via prop onAdd.
     Usa o padrão funcional de atualização de estado (prev => [...prev, novoItem])
     ao invés de depender do valor atual do estado diretamente. Isso evita
     condições de corrida em cliques rápidos (teste do "Cliquenildo" no TDD).

  3. Geração de ID com Date.now().toString()
     Cada item recebe um ID único baseado no timestamp em milissegundos.
     Isso garante que dois "Arroz" adicionados sequencialmente tenham IDs
     diferentes, então ao remover um, apenas ele some — sem o bug de
     "ID compartilhado" descrito no TDD.

  4. Função removerItem
     Recebe o id do item, usa .filter() para criar nova lista sem ele,
     e atualiza o estado. O React detecta a mudança e re-renderiza
     ShoppingList automaticamente. Também usa o padrão funcional (prev =>).

  5. Remoção de código desnecessário
     - Eliminados os três useState não utilizados (productName, quantity, price).
     - Eliminada a segunda instância de <ShoppingForm />.
     - Eliminada a renderização direta da mockShoppingList.
     - App agora renderiza apenas o título + <ShoppingForm> + <ShoppingList>.

  6. Estrutura JSX simplificada
     Um único <div className="app"> envolve tudo, sem fragmentos desnecessários.


================================================================================
  PARTE 2 — ShoppingForm.tsx: Validação, Reset e Props
================================================================================

Arquivo: src/components/ShoppingForm.tsx
Status: CONCLUÍDO

Decisões tomadas:

  1. Recebe onAdd via props
     O componente não sabe mais nada sobre a lista — apenas chama onAdd()
     quando o usuário clica em "Adicionar". Quem decide o que fazer com os
     dados é o App (separação de responsabilidades).

  2. Estado local apenas para os inputs
     Dois useState locais: nome (string) e quantidade (string).
     Nota importante: quantidade é string, não number. O motivo é que
     um campo <input type="number"> com value=0 exibe "0" na tela assim
     que o componente monta — confuso para o usuário. Usando string vazia
     ("") o campo começa visivelmente em branco, e convertemos para Number
     apenas no momento da validação/envio.

  3. Campo "Preço" removido
     O campo de preço não existe nos requisitos funcionais da atividade
     (atividade.md) nem no schema ShoppingItem (seed.ts). Era código extra
     que não pertencia aqui.

  4. Validações implementadas (handleAdicionar):

     a) Nome vazio ou só espaços:
        nome.trim() retorna string vazia se o usuário não digitou nada ou
        digitou apenas espaços. A função retorna sem fazer nada.
        Cobre: teste do "Vazio" e teste do "Espaço em Branco" do TDD.

     b) Quantidade inválida:
        Number(quantidade) converte a string para número.
        - Se a string for vazia: Number("") === 0 → bloqueado pelo !qtd.
        - Se for texto tipo "duas": Number("duas") === NaN → bloqueado
          por !Number.isFinite(qtd).
        - Se for zero: bloqueado por !qtd (0 é falsy).
        - Se for negativo: bloqueado por qtd <= 0.
        Cobre: teste da "Quantidade Zero ou Negativa" e "Texto na Quantidade".

  5. Reset dos campos após adicionar
     Após chamar onAdd(), os estados nome e quantidade voltam para "".
     Isso limpa os inputs visualmente na tela (RF03 da atividade).
     Cobre: teste da "Limpeza de Campos" do TDD.

  6. Prop min="1" no input de quantidade
     Impede o seletor de setas do browser de ir abaixo de 1.
     A validação no código continua sendo a barreira principal — o atributo
     min é apenas uma ajuda visual para o usuário.

--------------------------------------------------------------------------------
  CORREÇÃO PÓS-BUILD — verbatimModuleSyntax
--------------------------------------------------------------------------------

Após o primeiro build, o TypeScript apontou dois erros TS1484:
  "ShoppingItem is a type and must be imported using a type-only import
   when verbatimModuleSyntax is enabled."

O tsconfig.app.json do projeto usa verbatimModuleSyntax: true, que exige
que importações de tipos sejam marcadas com "import type" para que o
compilador saiba que pode descartar o import sem analisar o módulo inteiro.

Correções aplicadas:
  - src/App.tsx:          import { ShoppingItem }  ->  import type { ShoppingItem }
  - src/components/ShoppingList.tsx: idem.

Build final: sucesso — 0 erros, 0 warnings.

--------------------------------------------------------------------------------
  Novo arquivo: src/components/Modal.tsx
--------------------------------------------------------------------------------

Componente reutilizável que recebe:
  - isOpen: boolean      — controla se o modal é renderizado ou não
  - onClose: () => void  — callback chamado ao fechar (backdrop, botão ✕, Esc)
  - title: string        — título exibido no cabeçalho
  - children: ReactNode  — conteúdo variável (formulário ou confirmação)

Decisões:

  1. Renderização condicional com guard "if (!isOpen) return null"
     O componente não existe no DOM quando fechado — nenhum CSS de visibilidade
     (display: none / opacity: 0) foi usado. Isso evita que elementos dentro do
     modal (inputs, botões) recebam foco por Tab quando o modal está fechado.

  2. Fechar ao clicar no backdrop
     O backdrop tem onClick={onClose}. O card interno tem
     onClick={(e) => e.stopPropagation()} para que cliques dentro do card não
     propaguem para o backdrop e fechem o modal acidentalmente.

  3. Fechar com tecla Escape
     useEffect adiciona um listener de 'keydown' quando isOpen é true e o
     remove no cleanup. Isso é UX padrão esperado por usuários de teclado e
     leitores de tela. O listener é limpo automaticamente quando o modal fecha
     ou o componente é desmontado.

  4. aria-label="Fechar" no botão ✕
     O botão usa o caractere ✕ visualmente mas possui aria-label para que
     leitores de tela anunciem "Fechar" em vez de "x" ou "símbolo".

  @keyframes slideUp: translateY(16px)→0 + opacity 0→1 no card.

--------------------------------------------------------------------------------
  Fluxo completo pós-modal
--------------------------------------------------------------------------------

  ADICIONAR:
  Usuário clica "+ Adicionar Item"
    → isFormOpen = true → Modal (formulário) aparece
    → Usuário preenche nome + quantidade + clica "Adicionar"
    → handleAdicionar() valida → onAdd() → adicionarItem() no App
    → item adicionado à lista + isFormOpen = false → Modal fecha sozinho

  REMOVER:
  Usuário clica "Remover" em um item da lista
    → confirmarRemover(id) → confirmId = id → Modal (confirmação) aparece
    → Modal exibe "Remover 'Nome do Produto' da lista?"
    → Se "Cancelar": confirmId = null → Modal fecha, item intocado
    → Se "Remover": removerItem() filtra lista + confirmId = null → Modal fecha

--------------------------------------------------------------------------------
  Novo arquivo: src/hooks/useShoppingList.ts
--------------------------------------------------------------------------------

Custom hook que centraliza TODO o estado e as operações da lista de compras.
O App.tsx não declara mais nenhum useState — ele apenas consome o hook.

Estados encapsulados:
  shoppingList    — array de ShoppingItem, inicializado com mockShoppingList
  isFormOpen      — boolean, controla modal de adição
  confirmId       — string | null, ID do item aguardando confirmação de remoção

Funções exportadas:
  adicionarItem(nome, quantidade)
    Cria novo ShoppingItem com ID único (Date.now()), adiciona à lista e
    fecha o modal de adição. Usa padrão funcional (prev =>) para segurança
    em atualizações rápidas e consecutivas.

  confirmarRemover(id)
    Seta confirmId — não remove nada ainda. Apenas abre o modal de confirmação.

  removerItem()
    Lê confirmId e filtra a lista. Reseta confirmId ao final, fechando o modal.

  cancelarRemocao()
    Reseta confirmId sem modificar a lista.

Valor derivado (não é estado):
  itemParaRemover = shoppingList.find(item => item.id === confirmId)
    Não usa useState porque é 100% derivável do estado existente.
    Recalculado automaticamente a cada render. Usado para exibir o nome
    do item no modal de confirmação.

Inicialização com seed:
  useState<ShoppingItem[]>(mockShoppingList) substitui o array vazio anterior.
  O usuário abre o app e já vê 10 produtos na lista, permitindo testar
  remoção e adição sem precisar preencher dados manualmente primeiro.

--------------------------------------------------------------------------------
  src/db/seed.ts — adição do campo preco
--------------------------------------------------------------------------------

ShoppingItem ganhou o campo:
  preco: number  — valor unitário em reais

Cada item do mockShoppingList recebeu um preço realista de supermercado
(ex: Arroz 5kg → R$ 24,90; Perfume 100ml → R$ 89,90).
Os preços são estáticos no seed — servem apenas para popular o estado inicial.

--------------------------------------------------------------------------------
  src/components/ShoppingForm.tsx — campo de preço + mensagem de erro
--------------------------------------------------------------------------------

Novo campo:
  preco: string  — estado local do input de preço, igual a quantidade:
                   string vazia inicialmente, convertido para Number na
                   validação. input type="number" com step="0.01" para aceitar
                   centavos.

Novo estado:
  erro: string   — mensagem de erro exibida abaixo dos inputs.
                   Vazio = sem erro = elemento <p> não renderizado (condição {erro && ...}).

Lógica de erro:
  A validação em handleAdicionar percorre os campos na ordem nome → quantidade
  → preço. Ao encontrar o primeiro inválido, seta a mensagem correspondente e
  retorna sem prosseguir. Isso evita mostrar múltiplos erros ao mesmo tempo —
  o usuário corrige um por vez.

  Mensagens definidas:
    "O nome do produto não pode estar vazio."
    "A quantidade deve ser maior que zero."
    "O preço deve ser maior que zero."

limparErro():
  Chamada no onChange de todos os inputs. Limpa o estado erro quando o
  usuário começa a digitar após um erro — o feedback desaparece assim que
  ele interage, sem precisar tentar enviar novamente primeiro.

onAdd agora recebe três argumentos: (nome, quantidade, preco).

adicionarItem(nome, quantidade, preco):
  Adicionado o terceiro parâmetro preco, incluído no objeto novoItem.
  Nenhuma outra mudança — a lógica de ID, estado e fechamento de modal

--------------------------------------------------------------------------------
  src/components/ShoppingList.tsx — exibição de preço e total geral
--------------------------------------------------------------------------------

formatarPreco(valor):
  Função utilitária local que usa toLocaleString('pt-BR', currency: 'BRL').
  Formata automaticamente: 24.9 → "R$ 24,90", 89.9 → "R$ 89,90".
  Sem dependência externa — a API Intl.NumberFormat do browser faz o trabalho.

Cada item agora exibe três informações numéricas em .item-detalhes:
  - Qtd: N           — quantidade
  - R$ X,XX un.      — preço unitário
  - R$ Y,YY          — subtotal (preco × quantidade), em negrito

totalGeral:
  Calculado com .reduce() ao renderizar — soma preco × quantidade de todos
  os itens. Valor derivado, não armazenado em estado (recalculado a cada render).
  Exibido no rodapé .lista-total abaixo da lista, com destaque tipográfico.
